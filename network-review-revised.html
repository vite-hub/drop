Product network review: what's built, what's missing, what to prototype next

Checked against the network and Product Insights review notes. Implementation status reflects a local run against transformed fixture data.

Summary
  • The structure agreed in review is in place: the page centres on one focus node, planning-group branches expand one at a time, large columns fold into a Pareto "Cluster" node with a checklist, the table sits under the graph, and edge thickness shows each path's share.
  • Four follow-up decisions are still missing: focus a node from inside the graph, edge colour by connection type, sort by value with a quantity alternative, and an expand-all control. The node importance bar from the initial review is missing too.
  • A transformed manufacturing fixture exposes three trust problems that should come first. Nodes show "Usage 0 / mo" while the adjacent cluster shows 16,980 / month. Columns are mislabelled ("Final Goods" on a seal). Selecting one fastener highlights the entire network.
  • No reviewer can open the page on the preview today. The API returns 403 because the implementation adds a permission gate on top of the flag, although the agreed approach was flag-only.
Data handling default for agent-generated reviews

Use real-world data to learn the shape of the problem, then publish a transformed fixture. Replace identifiers, names, group labels, and dates; perturb quantities, costs, and timings; and keep only the relationships and edge cases needed to test the behavior. Apply independent transformations so a combination of values cannot be joined back to a source row.

Do not publish raw exports, exact customer or plant names, source URLs, commit hashes, or screenshots containing source values. Before sharing, search the finished document for distinctive names and exact value combinations. The reader should be able to understand the product problem without being able to recover the original record.

Transformed-fixture load times (local, warm): 0.6 s for 2 nodes, 1.1 s for 7, 0.9 s for 24, 1.5 s for 12, 3.4 s for 52. The availability check runs one recursive Cube query per product-page view while the flag is on.

Proposed next iteration

  1. Fix the semantics above: pulled demand on nodes, role-based column labels, directed highlight, no lead-time call. These are small changes, and without them a first user test produces wrong conclusions.
  2. Refocus from the graph (P5). Hovering a node shows "Focus here". Focusing navigates to /insights/:id/network, so browser back works, and a breadcrumb shows the focus history.
  3. Graph toolbar (P5): Sort (Value · Quantity · Cover risk), Expand all / Collapse all, Fit, and a legend that introduces edge colours: violet for assembly, sky for distribution, amber reserved for sales bundles.
  4. Node card with importance bar (P1 B) and compact Other node (P2 B).
  5. Horizontal collapse as a rail (P3 B), with defaults that depend on the case: collapsed only when the network crosses planning groups.
  6. Later: deck duplication, material units, routing steps, CSV export, the v2 tab preview (P6), and a separate lead-time timeline.

Open questions

  • Value sort needs a unit cost per product and planning group in Cube. If there isn't one, ship Quantity and Cover risk first.
  • Demand window: the page uses six months of history. The purchase-suggestion use case may need forward demand from the forecast instead.
  • Upstream default sort: in the follow-up review, "closest to running out" was floated for the case where a product has 70 components. Is Cover risk the default upstream and Value the default downstream?
  • Gate: keep the new app.product.network permission, or return to flag-only as decided in the initial review?
